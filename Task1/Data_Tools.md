## **2. МЕХАНИЗМ ТЕГИРОВАНИЯ ДАННЫХ**

Для управления защитой введем систему тегов (меток) конфиденциальности.

### **2.1. Классы тегов (Taxonomy)**
1.  **`confidentiality:public`** – Открытые данные (прейскурант, контакты клиники).
2.  **`confidentiality:internal`** – Внутренние данные (графики работы, внутренние регламенты).
3.  **`confidentiality:confidential`** – Конфиденциальные данные (ПДн: ФИО, телефон).
4.  **`confidentiality:restricted`** – Данные ограниченного доступа (Медицинские диагнозы, результаты анализов, финансовые транзакции).
5.  **`data_subject:patient`** – Субъект данных: пациент.
6.  **`data_subject:employee`** – Субъект данных: сотрудник.
7.  **`regulation:152-fz`** – Подпадает под 152-ФЗ.
8.  **`regulation:medical_secret`** – Подпадает под врачебную тайну (323-ФЗ).
9.  **`retention:1year`**, **`retention:5years`**, **`retention:75years`** – Срок хранения.

### **2.2. Инструменты и методы тегирования**
*   **На уровне базы данных:** Использование столбцов-меток в таблицах (например, `data_classification`). Расширения БД для управления метаданными (например, `pg_label` для PostgreSQL).
*   **На уровне приложения:** Аннотации в коде (например, `@DataClassification(level=Classification.RESTRICTED)`) для автоматической проверки политик доступа.
*   **На уровне файловой системы:** Использование атрибутов файлов в NTFS/ReFS или решение для классификации данных (Microsoft Purview Information Protection, Varonis).
*   **Сквозной контроль:** Внедрение **Data Catalog** (например, **Apache Atlas**, **Collibra**, **Alation**), который будет центральным реестром всех активов данных с их тегами, отслеживанием происхождения (Lineage) и политиками.

### **2.3. Процесс работы с тегами**
1.  **Классификация при создании:** При внесении новой записи пациента система автоматически присваивает теги `confidentiality:restricted`, `data_subject:patient`, `regulation:152-fz`, `regulation:medical_secret`.
2.  **Проверка в CI/CD:** В пайплайне развертывания (GitLab CI/CD, Jenkins) добавляется шаг **статического анализа кода (SAST)** и **проверки конфигураций** на наличие операций с тегированными данными без соответствующих защитных механизмов (например, попытка логировать поле с тегом `restricted` в открытый лог).
3.  **Применение политик:** Система контроля доступа (например, **Open Policy Agent - OPA**) читает теги данных и контекст запроса (роль пользователя, атрибуты) для принятия решения `разрешить/запретить`.
4.  **Мониторинг и алертинг:** SIEM-система (**Splunk**, **ELK Stack с модулем безопасности**) отслеживает доступ к данным с тегом `restricted` и генерирует алерт при аномальной активности (например, врач из другого филиала массово запрашивает карты пациентов).

## **3. ИНСТРУМЕНТЫ, СПОСОБЫ И МЕРЫ ДЛЯ ОБЕСПЕЧЕНИЯ КОНФИДЕНЦИАЛЬНОСТИ**

| Этап жизненного цикла данных | Инструменты и технологии | Организационные меры |
|-------------------------------|---------------------------|----------------------|
| **1. Сбор (Collection)** | - Формы с валидацией и маскированием на фронтенде.<br>- API Gateway с валидацией схемы входящих данных (Swagger/OpenAPI).<br>- Принцип Privacy by Design: сбор только необходимых полей. | - Обучение сотрудников ресепшена принципам минимальности данных.<br>- Чек-лист необходимых полей для каждой услуги. |

Мониторинг и Аудит (Monitoring & Audit)** | - **SIEM** (**Splunk**, **Wazuh**, **Elastic Security**) для агрегации логов.<br>- **DLP-система** (**Symantec DLP**, **Digital Guardian**) для контроля утечек на конечных точках и в сети.<br>- **UEBA** (User and Entity Behavior Analytics) модуль для обнаружения аномалий. | - Назначение ответственного за реагирование на инциденты (CIRT).<br>- Регулярное проведение учений по реагированию на утечки данных. |

## **4. КЛЮЧЕВЫЕ АРХИТЕКТУРНЫЕ ИЗМЕНЕНИЯ (ИТОГ)**

1.  **Централизованная МИС** заменяет Excel-файлы и общие диски.
2.  **Сквозное шифрование и тегирование** данных от точки ввода до хранения.
3.  **ABAC на основе тегов** вместо простого RBAC для гибкого контроля доступа.
4.  **Автоматическая интеграция** через защищенные API вместо ручного переноса.
5.  **Выделенный Data Lake** с обезличенными данными для BI/AI/ML, полностью изолированный от операционных ПДн.
6.  **Централизованный аудит и мониторинг** в SIEM с UEBA для обнаружения аномалий.
7.  **Принцип Privacy by Design**, заложенный в каждый новый сервис (минимизация, тегирование, безопасность по умолчанию).

Эти изменения позволят «Медикаменте» не только соответствовать требованиям законодательства РФ, но и безопасно масштабироваться, внедрять новые цифровые сервисы и повышать доверие клиентов.
